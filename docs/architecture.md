# Структура и запуск сервиса

Приложение развивается в одном репозитории. Python-код собирается в пакет `ozon_demand_service`, который можно установить в окружение веб-сервера, исполнителя Airflow или исследователя. Фронтенд, ноутбуки, файлы данных и конфигурация развёртывания имеют собственные каталоги. [PyPA о структуре `src`](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/)

```text
src/ozon_demand_service/     Python-пакет приложения
  ingestion/                импорт истории и Seller API, проверки качества
  storage/                  чтение и запись снимков, витрин и результатов
  forecasting/              подготовка спроса, признаки, обучение и прогноз
  planning/                 правила пополнения, оптимизация и объяснение плана
  jobs/                     общие сценарии расчёта для оркестратора и воркера
  evaluation/               бэктест прогноза и симуляция поставок на истории
  api/                      HTTP-маршруты, параметры запроса и ответы
config/                     параметры запуска приложения
data/                       форматы и небольшие синтетические примеры
experiments/notebooks/      исследования и сравнения моделей в Jupyter
migrations/                 изменения схемы БД при подключении хранилища
infra/airflow/dags/          расписание и вызовы функций из пакета
infra/mlflow/                настройки сервера экспериментов, если выбран MLflow
infra/object-storage/        конфигурация S3, если понадобится
infra/python/Dockerfile      образ пакета и образ с проверками
frontend/                   веб-кабинет
compose.yaml                локальная сборка и запуск контейнеров
tests/                      проверки по мере реализации компонентов
```

Это целевая схема, каталоги появляются вместе с реализацией. Границы модулей определяются их входами и выходами. Выбор инструментов и распределение работы обсуждаются отдельно.

- `ingestion` загружает CSV и данные API, сохраняет исходную выгрузку и приводит оба источника к общему формату. `storage` предоставляет чтение и запись, а `migrations/` описывает изменения схемы БД. Сырые данные, очищенные записи, признаки и результаты — слои хранилища. В Git хранятся их описания, миграции и синтетические примеры.
- `forecasting` и `planning` получают подготовленные входы и возвращают результаты. `jobs` соединяет их с хранилищем, сохраняет результат и статус запуска. Оркестратор вызывает этот сценарий по расписанию, а API ставит запрос менеджера в очередь для воркера. Для одного и того же набора входов оба пути используют одну реализацию расчёта.
- `evaluation` содержит повторяемые расчёты оценки. Бэктест измеряет качество прогноза. Симуляция поставок воспроизводит изменение запасов и затраты при разных правилах пополнения. Ноутбуки задают параметры эксперимента, вызывают эти функции и показывают результаты.

## Что согласовать перед первой интеграцией

| Стык | Что фиксируем |
|---|---|
| Данные → прогноз | Ключ строки, гранулярность, единицы, время среза и доступность признаков на эту дату. Для неизвестного остатка или цены описываем явный пропуск. Ноль означает наблюдаемое значение. |
| Прогноз → планирование | Товар, кластер покупателя, даты и горизонт, прогноз в штуках, квантиль или интервал при наличии, версия модели и ID снимка данных. Для первого прогона достаточно точечного прогноза. |
| Планирование → API и интерфейс | Товар, количество, кластер назначения, дата отгрузки и ожидаемая дата доступности к продаже. План хранится вместе с причинами рекомендаций, параметрами расчёта, версией модели и ссылками на входные снимки. |

После проверки реальных выгрузок запишите в `docs/` словарь полей и примеры этих трёх форматов. Существенные изменения контрактов фиксируйте рядом с ними и обсуждайте в PR. На первом этапе один синтетический набор должен проходить цепочку «импорт → простой прогноз → правило пополнения → сохранённый план».

## Что проверить при подключении сервисов

| Риск | Решение и проверка |
|---|---|
| **Импорты работают локально, но ломаются в образе** | На машине разработчика устанавливать пакет через `uv sync`. В образе устанавливать сборку пакета той же версии и проверять импорт и запуск из другой рабочей директории. Файлы из `config/` и `data/` передавать отдельно с явным путём. |
| **Зависимости Airflow конфликтуют с приложением** | Версию Airflow и его зависимости закрепить в отдельном окружении. Пакет приложения ставить в окружение, где выполняется задача. Если какая-то задача требует несовместимых библиотек, запускать её в отдельном окружении. Группы зависимостей одного uv-проекта участвуют в общем разрешении зависимостей. [Установка Airflow](https://airflow.apache.org/docs/apache-airflow/stable/installation/installing-from-pypi.html) · [Группы зависимостей uv](https://docs.astral.sh/uv/concepts/projects/dependencies/#dependency-groups) |
| **План по расписанию и план после пересчёта расходятся** | Оба вызывают одну реализацию планирования. Сохранять версию модели, момент среза данных и параметры каждого расчёта. Добавить сквозную проверку, что на одном и том же наборе входов оба пути публикуют одинаковый план. |
| **Старый прогноз или план невозможно воспроизвести** | Записывать коммит кода, ID неизменяемого снимка входных данных и точную версию модели. Хранить сами снимки и файлы моделей. Для первого пилота на одной машине можно использовать базу метаданных и постоянный Docker-том для файлов. Код расчёта ссылается на версии и ID, расположение файлов задаётся при развёртывании. [Хранилище артефактов MLflow](https://mlflow.org/docs/latest/self-hosting/architecture/artifact-store/) |

При подключении API и оркестратора повторяем сквозной прогон через оба входа и сверяем планы при одинаковом снимке и параметрах. Ноутбук импортирует тот же пакет из своего окружения.
