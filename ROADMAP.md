# План разработки сервиса поставок Ozon FBO

Цель прототипа — показать, как менеджер получает план поставок, меняет ограничения и выгружает результат. Для первой демонстрации берём одного продавца, около 20 товаров и 2–3 кластера. Для каждой рекомендации нужны товар, количество, кластер, дата отгрузки, ожидаемая дата доступности к продаже и причина расчёта.

В `HSE-001` уже есть корневые `pyproject.toml` и `uv.lock`, структура репозитория и сборка Python через Compose. Команды из README проверяют импорт пакета и запускают Ruff. Продуктовый API, ежедневный конвейер, прогноз и оптимизатор идут следующими этапами. Роли, конкретные инструменты и номера релизов ниже служат ориентирами для команды.

## Границы проекта

Один репозиторий и один устанавливаемый Python-пакет `src/ozon_demand_service/`. Веб-сервер, воркер, оркестратор и Jupyter используют этот пакет в своих окружениях. Общие зависимости приложения закреплены в корневом `uv.lock`. Версию и зависимости оркестратора закрепляем отдельно. Код приложения, настройки запуска и исходные данные подключаются к нужным контейнерам отдельно. Схема и форматы обмена описаны в `docs/architecture.md`.

| Где | За что отвечает |
|---|---|
| `ingestion/`, `storage/` внутри Python-пакета | Импорт CSV и Seller API, проверки качества, чтение и запись снимков и результатов. Миграции схемы хранятся в `migrations/`. |
| `forecasting/`, `planning/` | Прогноз спроса и расчёт поставки по подготовленным входам. |
| `jobs/`, `api/` | Сценарий расчёта и сохранение результата. API принимает запрос, воркер выполняет его, оркестратор запускает тот же сценарий по расписанию. |
| `evaluation/`, `experiments/notebooks/` | В `evaluation/` находятся повторяемые расчёты бэктеста и симуляции. В ноутбуках — анализ и интерпретация. |
| `frontend/`, `config/`, `infra/`, `compose.yaml` | Веб-кабинет, конфигурация приложения и запуск сервисов. |

На одной машине для первого пилота достаточно базы метаданных и постоянного Docker-тома для файлов моделей. Снимки данных храним по неизменяемым ID. В каждом запуске сохраняем коммит кода, срез данных, точную версию модели и параметры расчёта. MLflow можно подключить с локальным томом. S3 остаётся вариантом, если понадобится отдельное файловое хранилище.

## Очередность реализации

| Веха | Что делаем | Критерий готовности |
|---|---|---|
| **0. Данные и контракты** | Проверить пробные выгрузки Seller API, историю CSV и данные продавца. Согласовать SKU, кластер покупателя и кластер хранения, глубину истории, даты приёмки, источники затрат и смысл пропусков. Описать вход прогноза, вход планировщика и результат плана. | В `docs/` есть словарь полей, схемы обмена и маленький синтетический пример. Для недоступных полей зафиксированы ограничения или допущения. |
| **1. `v0.1.0` — первый сквозной расчёт** | Импортировать синтетические данные, собрать простой прогноз и правило пополнения. Сохранить план и показать результат в таблице или CSV. Добавить сквозную проверку в контейнере. | Из чистого клона повторяется цепочка «импорт → прогноз → поставка → сохранённый план». Результат сходится с ручным расчётом и воспроизводится без ключа Ozon. |
| **2. `v0.2.0` — ежедневные данные** | Подключить исторический импорт и Seller API. Настроить загрузку по расписанию, снимки остатков и товара в пути, проверки качества, повторный запуск и догрузку прошлых дат. | Повторный импорт обновляет записи без дублей. При сбое видна дата последнего успешного среза. Пропуски отличаются от наблюдаемых нулей. |
| **3. `v0.3.0` — прогноз и версии моделей** | Сравнить бейзлайн с моделями, выбранными для эксперимента. LightGBM — один из кандидатов. Оценить ошибку на временных срезах и проверить калибровку квантилей, если используем вероятностный прогноз. Подключить сохранение версий моделей. | Из зафиксированного снимка воспроизводятся метрики. Каждый сохранённый прогноз связан с датой среза и точной версией модели. |
| **4. `v0.4.0` — оптимизация и API** | Формализовать стоимость хранения, дефицита и доставки, сроки и ограничения приёмки. Сравнить правило пополнения с оптимизатором. OR-Tools — один из кандидатов. Подключить сохранение версий плана и асинхронный пересчёт через API. | На малом примере план допустим и сопоставим с ручным перебором. Для одного среза, прогноза и набора ограничений план через API совпадает с планом по расписанию. |
| **5. `v0.5.0` — кабинет и эксплуатация** | Показать план, прогноз и причины рекомендаций. Добавить изменение параметров и выгрузку. Подключить наблюдение за свежестью данных, сбоями и временем расчёта. | Менеджер проходит цепочку от просмотра до выгрузки. Команда поднимает необходимый стек через Compose и видит, когда обновлялись данные. |
| **6. `v1.0.0` — оценка и защита** | Проиграть историю с учётом сроков поставки и движения запасов. Сравнить прогнозы с одним планировщиком и правила планирования с одним прогнозом. Подготовить дизайн A/B-теста и при наличии пилота вести журнал принятых и исполненных решений. | С тега повторяется демонстрация. Отчёт показывает точность прогноза, оценку затрат и доступности в симуляции. Фактические результаты пилота описаны отдельно, если он состоялся. |

Проверку реальных выгрузок можно начать одновременно с каркасом импорта. После согласования стыков фронтенд может использовать пример ответа API, а прогноз и расчёт поставок — общий синтетический набор. A/B-тест можно проводить после проверки, что группы достаточно независимы с учётом общего запаса.

## Git и проверки

- Создаём ветку под задачу от согласованной базы, например `HSE-002`. У задачи есть входы, ожидаемый результат и критерий приёмки. Один PR вносит одно проверяемое изменение, его смотрит другой участник команды. Изменения контрактов сопровождаем обновлением примеров в `docs/`. [Связь PR с задачей](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)
- В CI сначала добавляем сборку Python и Ruff через Compose. С появлением кода добавляем тесты импорта, прогнозирования и планирования, запуск миграций на чистой базе, проверку загрузки DAG и сборку фронтенда. Проверки запускаем на синтетических данных. [Пример CI бэкенда FastAPI](https://github.com/fastapi/full-stack-fastapi-template/blob/master/.github/workflows/test-backend.yml)
- В Git храним код, конфиги без секретов, миграции, контракты, синтетические данные и ноутбуки с безопасными выводами. Выгрузки продавца, ключи, файлы моделей и приватные результаты остаются в закрытом хранилище. Для экспериментов фиксируем версию набора, временные срезы и метрики. [Публикация методов и результатов M5](https://github.com/Mcompetitions/M5-methods)

Первые проверки предметной логики:

1. Импорт одного среза дважды сохраняет то же количество записей. Пропуск выгрузки не записывается как нулевой спрос.
2. Товар в пути прибавляется к доступному остатку только после ожидаемой приёмки. Партия учитывается один раз.
3. При 30 доступных единицах, коробе из 10 и потребности 20 + 20 план распределяет не больше трёх коробов и показывает непокрытую потребность.
4. При расчёте на историческую дату признаки строятся из информации, известной к этому моменту. Будущие фактические значения используются для оценки.
